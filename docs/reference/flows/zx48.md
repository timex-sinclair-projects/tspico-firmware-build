# Flow: `tpi:zx48` and life in Spectrum mode

The TS-Pico can turn the 2068 into a ZX Spectrum: the 2068 runs a Spectrum
ROM from its DOCK bank, and the Pico switches to a second service loop
that speaks that ROM's much simpler protocol — one command byte, a
ready-wait, then a block streamed with no pre-header, no session, no SYNC
and no status. This flow follows the switch, a `LOAD ""`, a
`LOAD "tpi:name"`, a `SAVE "tpi:dir"`, a `SAVE`, and the way back. User's
view: [user manual chapter 9](../../manual/user-manual.md#chapter-9-zx-spectrum-mode);
the ROM: [../rom/zx48.md](../rom/zx48.md).

Notation as in [command.md](command.md): **TX**/**RX** the bus FIFOs, **Y**
the status on port 0Fh, which the Spectrum ROM polls only for READY (bit
6).

## Into ZX48 mode

| # | Side | What happens | TX / Y |
|---|---|---|---|
| 1 | 2068 | `LOAD "tpi:games.tap"`: a tape mounted, as in [command.md](command.md#a-mount-load-tpigamestap) | [01] / `FF` |
| 2 | 2068 | `SAVE "tpi:zx48" CODE a,b`: an ordinary command | |
| 3 | Pico | `ZX48` ([../firmware/tspico-commands.md](../firmware/tspico-commands.md#zx48pre-cmd)): `TSP.zx48 = True`; the loader from `b` (1 normal, 2+ the compatible one, ≥ 16384 also its buffer size); the instructions, shown unless `a` is 1; `PROCESS_CMD`'s tail as usual | [01] / `FF` |
| 4 | Pico | `TS2068_IO` sees `TSP.zx48` after the command: stops the pre-header DMA channel and calls `ZX48_IO(pre)` with this command's pre-header (its `CODE` numbers) ([../firmware/tspico-dispatch.md](../firmware/tspico-dispatch.md#zx48_iopre)) | |
| 5 | Pico | `ZX48_IO`: a fresh `TS_IO_DUAL` (the pre-load is lost with the old FIFO), Y = READY; the loop waits for a byte | [] / `FF` |
| 6 | 2068 | `OUT 244,3`: port F4h, the HSR = 3 — chunks 0 and 1 from the cartridge bus, which at the BASIC prompt (port FFh bit 7 clear) is the DOCK: slot `DCK_SLOT`, the Spectrum ROM v4 at 0000h–3FFFh. The Z80 is now executing it: "© 1982 Sinclair / TS-Pico ZX v4" | |

The 2068's own ROM is out of the picture until step "Back" below: no SYNC,
no TPMODE, no function chain. The Pico's ROM and bank state machines keep
serving the slots as before.

## `LOAD ""`

The Spectrum ROM's LD-BYTES (patched by Ricardo's TS-Pico ROM and v2):

| # | Side | What happens | What can go wrong |
|---|---|---|---|
| 1 | Spectrum | `DI`; `OUT (0Eh),'L'` | |
| 2 | Pico | `ZX48_IO` takes `'L'` (76); waits ≤ 3 s for a core-1 flash write; `LOAD_ZX` (or `LOAD_ZX_C`, the whole tape in RAM, with the compatible loader) ([../firmware/tspico_io.md](../firmware/tspico_io.md#load_zxmq-tsp)) | |
| 3 | Spectrum | WAIT_RDY: polls 0Fh up to ~3.8 s (v3 fixed v2's version, which corrupted DE and moved the wrong number of bytes) ([../rom/zx48.md](../rom/zx48.md#wait_rdy_v3-3874h)) | no READY: `RET NC`, the ROM's "load failed": Report R |
| 4 | Pico | the next block of the mounted tape (or `nofile.tap`) read into RAM, `gc.collect()`; **the flag first, then READY**; the rest by DMA | READY before the flag: the Z80 reads 00h |
| 5 | Spectrum | reads the flag and the block blind at its own pace, checks the flag and the checksum as on a real tape | an empty FIFO: R |
| 6 | Pico | the pointer moves on (and wraps at the end of the tape); any bytes the ROM did not read are flushed | |

No status, no echo, no pre-load: the block is the whole answer. A header
that does not match is just skipped by the ROM, which sends `'L'` for the
next — the Pico serves blocks in tape order.

## `LOAD "tpi:manic.tap"` (v3, v4)

| # | Side | What happens |
|---|---|---|
| 1 | Spectrum | SA-ALL fetches the name at 0631h, which now calls `TPI_CHK`: a name starting `tpi:` (any case) goes to `TPI_CMD`, which will finish the statement itself ([../rom/zx48.md](../rom/zx48.md#tpi_chk)) |
| 2 | Spectrum | `OUT (0Eh),'T'`; WAIT_RDY (~3.8 s; none → Report J: no Pico, or firmware without `'T'`) |
| 3 | Pico | `ZX48_IO` takes `'T'` → `ZX_TPI()`: says READY once ready to receive ([../firmware/tspico-dispatch.md](../firmware/tspico-dispatch.md#zx_tpi)) |
| 4 | Spectrum | the op (T_ADDR: 1 LOAD; v4 sets bit 7), the length, the name after `tpi:`, ~55 µs a byte |
| 5 | Spectrum | waits for READY up to ~30 s, testing BREAK every ~0.24 s (Report D) |
| 6 | Pico | op 1: `LOAD_TPI(name)` — the card mounted, the file copied to the Pico's flash, the block table built — the folder re-read first if a ZX SAVE made it stale; the reply built in RAM: a status (FFh OK, else an ERR_NR from `ZX_REPORT`), then the message (v3: one length and the text; v4: pieces, then 0); streamed, READY once it moves |
| 7 | Spectrum | reads the status and the text, prints it on the upper screen; FFh → "0 OK"; else `TPI_ERR` raises the report by hand |

## `SAVE "tpi:dir"` (v4)

The same exchange with op 80h (SAVE, pieces). The firmware lists the
current folder as `CAT` does on the 2068 (or `tpi:dir games`, a pattern),
in pieces of up to 255 bytes; the Spectrum prints each with PR-STRING, and
its own "scroll?" pauses the stream as long as the user likes. A v3 ROM
(op without bit 7) gets "SAVE \"tpi:dir\" needs ZX ROM v4". Other `tpi:`
words in ZX48 mode: Report Q.

## `SAVE "name"`

| # | Side | What happens | What can go wrong |
|---|---|---|---|
| 1 | Spectrum | the header: `DI`; `OUT (0Eh),'S'`; SAVE_WAIT (WAIT_RDY; no READY → Report R, before anything is sent) | |
| 2 | Pico | `ZX48_IO` takes `'S'` → `SAVE_ZX`: `RX_BLOCK(…, 21, "ready")` — READY once listening ([../firmware/tspico_io.md](../firmware/tspico_io.md#save_zxmq-tsp)) | |
| 3 | Spectrum | length lo, hi, flag 00h, 17 header bytes, checksum — no handshake | |
| 4 | Pico | checks: a tape header (length 17, flag 0, parity); room for the data block | a bad header: logged, the rest drained; the ROM's data block never gets READY → R after ~3.8 s |
| 5 | Spectrum | ~1 s later the data block: `'S'`, WAIT_RDY, length, flag FFh, the bytes, checksum | |
| 6 | Pico | `RX_BLOCK` for it; its parity; the name checked (`SAVE_NAME`: no `?:*\/|"<>`); both blocks rewritten as TAP blocks; **the card mounted** (`ENA_SD` → `SAVE_MOUNT`; a swapped card noticed here), `cur_path/name.tap` written, `TSP.listing_stale` set; `ENA_MQ_DUAL` rebuilds the bus and says READY ([sd-handover.md](sd-handover.md)) | a write failure: logged only — the Spectrum got no status and believes the SAVE worked |

The Spectrum reads nothing back after a SAVE (SA-BYTES ends with `EI` /
`RET`), so a failed write after the data block cannot be reported; a refusal
is only possible before the data block, by withholding READY.

## Back to the 2068

| # | Side | What happens |
|---|---|---|
| 1 | 2068 | `OUT 244,0`: all chunks from HOME again; the 2068's BASIC is back, its state as it was before step 6 of "Into" (the Spectrum ROM used the same RAM, so programs and variables may have been overwritten) |
| 2 | 2068 | `OUT 14,14`: port 0Eh, value 0Eh |
| 3 | Pico | `ZX48_IO` takes 14: `TSP.zx48 = False`; any bytes left in TX flushed and the state machine restarted; back to `TS2068_IO`, which re-arms the pre-header channel |
| 4 | 2068 | the next command's SYNC: `MQ_TO_IDLE` stages the pre-load — TX [01], `FF` ([break-and-recovery.md](break-and-recovery.md)) |

No pre-load is staged on the way out; ROM 2.x's SYNC makes that harmless.
On ROM 1.1 (no SYNC) the next command would read 00h and get J *(audit §2
#12; unverified on hardware)*. The old way out, `OUT 10,100`, no longer
works: the dual-port PIO answers only ports 0Eh and 0Fh.

## What goes wrong, and where

| Failure | The Spectrum sees |
|---|---|
| no Pico, or ZX48 mode not entered (`OUT 244,3` without `tpi:zx48`) | every LOAD/SAVE: R after ~3.8 s; `LOAD "tpi:"`: J |
| a game with its own turbo loader | it does not go through LD-BYTES: it cannot load from the Pico; the compatible loader helps only loaders that do |
| the FIFO ran dry mid-block | R |
| BREAK at `TPI_CMD`'s long wait | D |
| a ZX SAVE that fails on the card | nothing: logged on the Pico only |
