# The ZX Spectrum ROM

Source: [`src/rom/patches/tspico-zx48-v3.asm`](../../../src/rom/patches/tspico-zx48-v3.asm)
(all 280 lines), which builds ZX v4, [`src/rom/TSPICO-ZX48-V4.BIN`](../../../src/rom/TSPICO-ZX48-V4.BIN),
with `-DZXV=4`, from the base image [`ROMs/TSPICO-ZX48-V2.BIN`](../../../ROMs/TSPICO-ZX48-V2.BIN);
the base image's own patch is in [PATCH_ZX48_HANDSHAKE.md](../../rom-analysis/PATCH_ZX48_HANDSHAKE.md).

The TS-Pico can turn a 2068 into a ZX Spectrum: flash slot 0 holds a
modified 48K Spectrum ROM, which the 2068 runs from its DOCK bank, and
whose tape routines talk to the Pico instead of the cassette port. This
chapter is that ROM's TS-Pico changes, layer by layer, in the ZX v4 that
ships, and how ZX48 mode is entered and left. The firmware's side is `ZX48_IO` and `ZX_TPI`
([../firmware/tspico-dispatch.md](../firmware/tspico-dispatch.md#zx48_iopre))
with `LOAD_ZX`, `LOAD_ZX_C` and `SAVE_ZX`
([../firmware/tspico_io.md](../firmware/tspico_io.md#zx48-mode)); the whole
sequence is [the ZX48 flow](../flows/zx48.md); the user's view is
[user manual chapter 9](../../manual/user-manual.md#chapter-9-zx-spectrum-mode).

Addresses here are Spectrum ROM addresses (the image is a single 16K ROM,
file offset = Z80 address). The Spectrum's system variables are at the same
addresses as the 2068's where the two agree ([sysvars.md](sysvars.md#the-zx-spectrum-roms-variables)).

## The layers

| Image | crc32 (16K) | What it adds |
|---|---|---|
| stock 48K | — | Sinclair's |
| TS-Pico ZX ROM (Ricardo) | `029861D1` | LD-BYTES and SA-BYTES send `'L'`/`'S'` on port 0Eh and move the block through it, paced by fixed delays; `OUT (FFh),A` at boot (386Eh). No use of port 0Fh at all |
| the base image, `ROMs/TSPICO-ZX48-V2.BIN` | `B3D40C73` | a READY handshake on 0Fh once per block (WAIT_RDY at 3874h, SAVE_WAIT at 388Ah) and the "(c) 1982 Sinclair / TS-Pico ZX" banner with a version digit; 78 bytes ([PATCH_ZX48_HANDSHAKE.md](../../rom-analysis/PATCH_ZX48_HANDSHAKE.md)) |
| **ZX v4**, `TSPICO-ZX48-V4.BIN` | `2BA800EF` | WAIT_RDY rewritten (the base image's broke every transfer, below); `LOAD "tpi:name"` and `SAVE "tpi:dir"`, the op with bit 7 set and the reply in pieces; banner "v4"; 206 bytes from the base image. Flash slot 0 (`083655BF` padded to 32K) |

The base image and ZX v4 need the dual-port firmware: Ricardo's newer "Spectrum
nuevo LD" image polls 0Eh for the single-port firmware's `40h`, which the
dual-port firmware no longer sends, and is not a base for these
([PATCH_ZX48_HANDSHAKE.md §7](../../rom-analysis/PATCH_ZX48_HANDSHAKE.md#7-do-not-apply-this-to-spectrum-nuevo-ldrom)).

## Entering and leaving ZX48 mode

1. On the 2068, mount a tape (`LOAD "tpi:games.tap"`) — LOAD in ZX48 mode
   reads the mounted TAP.
2. `SAVE "tpi:zx48" [CODE a,b]`: the firmware answers, sets `TSP.zx48`,
   and after the command switches its loop to `ZX48_IO`
   ([../firmware/tspico-commands.md](../firmware/tspico-commands.md#zx48pre-cmd)).
   `b` picks the loader (1 normal, 2+ compatible, ≥ 16384 its buffer).
3. `OUT 244,3`: port F4h, the HSR, = 3 — chunks 0 and 1 from the cartridge
   bus; with port FFh bit 7 clear (as it is at the BASIC prompt) that is
   the DOCK, slot 0, the Spectrum ROM, at 0000h–3FFFh. The 2068 now runs
   it from its reset: "© 1982 Sinclair / TS-Pico ZX v4".
4. Back: `OUT 244,0` (all chunks from HOME again), then `OUT 14,14` —
   port 0Eh, value 0Eh — which `ZX48_IO` takes as "leave ZX48 mode". The
   port is 0Eh because the dual-port PIO answers only 0Eh and 0Fh; the old
   `OUT 10,100` stopped working with the single-port firmware.

The DOCK slot is `DCK_SLOT` in `config.ini` (0 by default) or `tpi:dock`;
the ROM must be in whichever slot the DOCK shows.

## The protocol in ZX48 mode

The Spectrum ROM opens every transfer with one byte on port 0Eh:

| Byte | Statement | Then |
|---|---|---|
| `'L'` (4Ch) | LOAD, VERIFY, MERGE: a block wanted | READY wait; the flag, the bytes, read with fixed delays |
| `'S'` (53h) | SAVE: a block to write | READY wait; the length, the flag, the bytes, the checksum |
| `'T'` (54h) | `LOAD "tpi:…"`, `SAVE "tpi:…"` | `TPI_CMD` below |
| `0Eh` | `OUT 14,14` from BASIC | the Pico leaves ZX48 mode |

There is no pre-header, no session and no SYNC: these are the 2068 ROM's
inventions. Inside a block the cadence is the ROM's fixed delays; the
Pico's TX FIFO depth paces the stream, as for the 2068's LOAD. The details
of each transfer are in the firmware chapters, which follow these bytes.

## The `EQU`s

| Name | Value | Meaning |
|---|---|---|
| PORT_DATA, PORT_STATUS | 0Eh, 0Fh | the TS-Pico's ports (the names are [exrom-sync.md](exrom-sync.md)'s too) |
| `WAIT_RDY` | 3874h | the base image's ready-wait, rewritten in place as `WAIT_RDY_V3` |
| `STK_FETCH` | 2BF1h | STK-FETCH: DE = start, BC = length of the string on the calculator stack |
| `CHAN_OPEN` | 1601h | CHAN-OPEN: select stream A |
| `PR_STRING` | 203Ch | PR-STRING: print BC bytes from DE |
| `BREAK_KEY` | 1F54h | BREAK-KEY: NC = CAPS SHIFT + SPACE (not the 2068 EXROM's BREAK_KEY at 2009h, [exrom-chunk1.md](exrom-chunk1.md#break_key-2009h)) |
| `SET_STK` | 16C5h | the tail of ERROR-2: clear the calculator stack and go on into the error report |
| `T_ADDR` | 5C74h | set by SA-ALL: 0 SAVE, 1 LOAD, 2 VERIFY, 3 MERGE |
| CH_ADD | 5C5Dh | the next character of the line |
| `X_PTR` | 5C5Fh | where the error marker goes |
| ERR_SP | 5C3Dh | the error handler's stack frame |
| `ERR_D` | 0Ch | ERR_NR for "D BREAK - CONT repeats" |
| `ERR_J` | 12h | ERR_NR for "J Invalid I/O device" |
| `NEW_CODE` | 38B8h | free (`FFh`) after the base image's banner, to 3CFFh: where the new code goes |
| `ZXV` | 4 | which image to build; `tools/build-rom.sh` sets it to 4 with `-DZXV=4` for ZX v4. Selects the output file, the banner digit and the code for `SAVE "tpi:dir"` and the reply in pieces |

CH_ADD and ERR_SP are named in `fddcmd.asm` too, with the same addresses;
the reference index files them there.

## The patch sites

| Address | Base image | ZX v4 | Why |
|---|---|---|---|
| 0631h | `CALL 2BF1h` (STK-FETCH) | `CALL TPI_CHK` | SAVE, LOAD, VERIFY and MERGE all fetch their name here in SA-ALL, before the ROM cuts it to 10 characters, so the whole name reaches `TPI_CHK` |
| 3874h–3889h | its WAIT_RDY | `WAIT_RDY_V3`, the same 22 bytes or fewer | the base image's broke every transfer |
| 38B7h | `'2' OR 80h` | `'4'` OR 80h | the last character of the banner |
| 38B8h–… | `FFh` | `TPI_CHK` … `TPI_END` (to 3979h) | the new code |

The base image's other sites are kept: 0563h (LD-BYTES: `CALL 3874h / RET NC` after
`'L'`), 04CCh (SA-BYTES: `CALL 388Ah / NOP` after `'S'`), 388Ah
(SAVE_WAIT: `CALL 3874h / RET C / EI / RST 8 / DEFB 1Ah` — Report R if the
Pico never gets ready; `RST 8` because SA-BYTES has a pushed AF a bare
`RET` would take), and the boot hook at 386Eh–3873h with the banner table
at 3898h. [`rom_zx48_hosttest.py`](../../../src/test/rom_zx48_hosttest.py)
checks that only these bytes differ from the base image, that the new code
sits in space the base image had free, that the committed image is what the source builds
(with sjasmplus), and runs the new code in a small Z80 interpreter against
a scripted Pico.

## `WAIT_RDY_V3` (3874h)

```text
WAIT_RDY_V3: LD B,4               ; 4 x 65536 polls
.outer:      LD HL,0
.poll:       IN A,(0Fh) / AND 40h ; READY?
             JR NZ,.ready
             DEC HL / LD A,H / OR L   ; (leaves carry clear)
             JR NZ,.poll
             DJNZ .outer
             RET                  ; timed out: carry clear
.ready:      SCF / RET            ; READY: carry set
```

About 3.8 s (4 × 65 536 polls of about 51 T-states at 3.5 MHz). Corrupts
A, B and HL; keeps DE and IX.

The base image's version used **D** as its outer counter and returned with D = 4. Both
callers — LD-BYTES at 0563h and SA-BYTES through 388Ah — hold the block
length in DE, so every ZX48 LOAD and SAVE moved 0400h + (length AND FFh)
bytes: a 6912-byte screen stopped after 1024 (Report R), and a 17-byte
header read 1041, zeros past the end of the block over whatever followed
the header buffer (the checksum still passed, because the extra bytes were
zeros). Found on hardware 2026-09-27. The rewrite keeps the entry, the
size (an `ASSERT` keeps it below SAVE_WAIT at 388Ah) and the timeout; B and
HL are set again by both callers before they use them.

The poll runs under the tape routines' `DI`, so a Pico that never answers
freezes the Spectrum for the 3.8 s before the report, as a tape error does.

## `LOAD "tpi:…"` and `SAVE "tpi:…"`

### `TPI_CHK`

Replaces SA-ALL's `CALL STK-FETCH` at 0631h.

1. `CALL STK_FETCH`: DE = the name, BC = its length — what SA-ALL expected.
2. A length of 256 or more, or under 5 → `RET`: not ours, SA-ALL goes on.
3. Compare the first four characters with `TPI_TXT`, each `OR 20h` (so
   upper or lower case; `:` is unaffected). A mismatch → restore DE and
   BC, `RET`: the stock path.
4. A match: `POP AF` drops the return into SA-ALL, so `TPI_CMD`'s `RET`
   goes to the statement's caller (STMT-RET): the statement is finished by
   `TPI_CMD`, never by the tape code. DE = the name after `tpi:`, C = the
   whole length.

Every other name takes the base image's path, unchanged.

### `TPI_TXT`

`"tpi:"`, lower case, for the comparison.

### `TPI_CMD`

1. C = the length after `tpi:` (1–251).
2. `OUT (0Eh),'T'`. `WAIT_RDY` (DE and BC saved): no READY in ~3.8 s →
   `TPI_ERR` with Report J — no Pico, or firmware without the `'T'`
   command, which treats it as an unknown byte and never says READY.
3. **The op**: T_ADDR — 0 SAVE, 1 LOAD, 2 VERIFY, 3 MERGE — with **bit 7
   set in ZX v4** (80h + T_ADDR): "send the reply in pieces". The firmware
   still answers an op with bit 7 clear, from an older Spectrum ROM, with a
   single length, and answers `SAVE "tpi:dir"` from one with "needs ZX ROM
   v4".
4. **The length** C, then **the name**, each byte through `TPI_OUT` (~55 µs
   apart, so the Pico's 4-deep RX FIFO never overflows; the firmware reads
   them in a loop).
5. **The wait**: up to 128 rounds of 16 384 polls of 0Fh (about 0.24 s
   each, ~30 s in all) — mounting copies the file to the Pico's flash, which
   takes seconds. After each round, `BREAK_KEY`: BREAK → `TPI_ERR` with
   Report D. All rounds gone → Report J.
6. **The status** (`IN A,(0Eh)`), kept: FFh = OK, anything else an ERR_NR
   value (0Eh F, 19h Q, 12h J …) chosen by the firmware's `ZX_REPORT`
   table ([../firmware/tspico-state.md](../firmware/tspico-state.md#zx_report)).
7. **The text**, after `TPI_DLY`, in pieces: a length (1–255; 0 = no
   text), that many bytes into a 255-byte workspace buffer (made once with
   `RST 30h`), printed on the upper screen with `PR_STRING`, then the next
   piece's length, until a 0. A listing longer than one byte's worth arrives
   in pieces, and the Spectrum's own "scroll?" handles a long one — it may
   wait as long as the user likes, between pieces, while the Pico waits.
   One ENTER (`RST 10h` with 0Dh) after text; none if there was none.
8. Status FFh → `RET`: "0 OK", and the program goes on (step 4 of
   `TPI_CHK` made this the statement's return). Anything else falls into
   `TPI_ERR`.

Firmware: `ZX_TPI` ([../firmware/tspico-dispatch.md](../firmware/tspico-dispatch.md#zx_tpi))
— op 1 mounts (by name or number, as `LOAD "tpi:"` on the 2068), op 0
with `dir` lists the folder (ZX v4 only); other ops and words are Report Q.
[`zx48_tpi_hosttest.py`](../../../src/test/zx48_tpi_hosttest.py) runs it
against these bytes.

Beware: `TPI_CMD` reads the whole reply — status, lengths, text — without a
ready-wait between bytes, as the 2068 ROM reads a message. The firmware
builds the reply in RAM and streams it into the FIFO (by DMA where it can),
saying READY once the stream is moving; while the Spectrum sits at its own
"scroll?" the stream simply stops, up to the firmware's stall limit, and
then goes on. A `TPI_DLY` before each read keeps the Z80 behind the
stream.

### `TPI_ERR`

Raises the report in A by hand, as `RST 8` would: `LD (IY+0),A` (ERR_NR),
X_PTR = CH_ADD (the error marker), `LD SP,(ERR_SP)`, `JP SET_STK` — the
tail of ERROR-2, which clears the calculator stack and returns into the
error handler ERR_SP points at. `RST 8` cannot be used because the code
byte must follow it in memory, and here the code is in A.

### `TPI_OUT`

`OUT (0Eh),A`, then falls into `TPI_DLY`: one byte to the Pico and about
50 µs for its RX FIFO. Keeps BC and DE.

### `TPI_DLY`

`PUSH BC / LD B,10 / DJNZ $ / POP BC / RET`: about 45 µs (the comment's
figure; with the `CALL` it is closer to 50). Keeps B, C and DE.

### `TPI_END`

The end of the new code; an `ASSERT` keeps it below 3D00h, where the
character set begins (the free space is 38B8h–3CFFh).
