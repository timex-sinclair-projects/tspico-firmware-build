# TS-Pico firmware: assumption audit (2026-09-30)

**Scope:** every hardcoded value, threshold, timeout, retry count, guard and workaround in `src/TS/*.py`, `src/main.py`, `src/manifest.py` and `src/config.ini`, checked for assumptions that may have outlived their reason. Style and general optimisation were out of scope.

**How it was done:**
- Six parallel passes, each over one slice and each in its own worktree:
  - `tspico.py`, in four slices;
  - `tspico_io.py`;
  - the small modules (`sdcard`, `channels`, `catalog`, `printer`, `native`, `extcmd`, `main.py`, `manifest.py`, `config.ini`).
- Each item's origin was traced through `git blame`. Two commits that touched every line were skipped: `--ignore-rev c897e91` (#57, line endings) and the #13/#25 moves. PR and issue text was read where there was one.
- Anything older than git history (`b2758a5`, 2026-05-03) was traced through `archive/tspico-ryan.py` and its changelog.
- Experiments were edits followed by the 34 host tests on Python 3.13, then reverted. Nothing was committed, and the Pico was not touched.

**Limits:**
- **"Tests pass" is not treated as evidence on its own.** Large parts of the firmware have no host coverage: the `TS2068_IO` dispatch, `ZX48_IO`, `GETLOG`, `CDIR`, `FWD`/`REW`, `COPY_FILE`, `PROCESS_ASM`, the old-ROM paths and SEND_MSG2's keyword widths.
- **The `tspico_io.py` pass ran no experiments.** The auto-mode permission classifier blocked its edits and some of its greps and blames. Its items rest on reading the code.
- **Line numbers** are for `main` (2d134dd). On branch `claude/send-msg2-line-tracking-e3c55b`, `tspico.py` lines after 1818 are 2 lower.
- **Nothing here was observed on hardware.** "Reproduced" means reproduced on the host with the test fakes.

## To do (outstanding, not from the audit)

- **Add `SAVE "tpi:dir"` support to the ZX48 ROM.** Requested 2026-10-01. Today ZX48 mode has `tpi:` LOAD only (ZX v3 ROM hook at 0631h, `LOAD "tpi:..."`). A directory listing from the Spectrum side needs a SAVE hook in the ZX ROM and a reply path in `ZX48_IO`/`ZX_TPI`, which caps replies at 200 bytes and uses default code 0x19 (#72).

---

- **Characters the 2068 redefines: show them so they can be typed back** (agreed 2026-10-01). The 2068's character printer (HOME `063Bh`) prints `0Ch` as DELETE, `7Ch` `|` as STICK and `7Eh` `~` as FREE **always**. It prints `7Bh` `{`, `7Dh` `}` and `7Fh` `©` as ON ERR / SOUND / RESET **unless FLAGS bit 4 is set**. Boot sets that bit before the copyright message (`0DE3`), and the line lister copies the in-quotes flag into it (`1683`), so its state when the Pico's text is printed is whatever was left behind. None of these five can be typed as a character on the 2068 keyboard.
  - **Text from a Mac or PC** (SD names, text files, help): show any character the 2068 can't print or type (these five, and anything ≥ 80h) as `?`, translated on the Pico. Today `|`/`~` become the letters " STICK "/" FREE " in `xstr()`, `~` becomes `?` in `catalog.dir_rows()`, and `{`, `}` and `©` aren't handled at all.
  - **Typing it back:** `LOAD "tpi:…"` (`LOAD_TPI`) should try an exact match first, then `catalog.match()` with `?`/`*` as wildcards, mounting only if **exactly one** file matches (several: F, and tell the user to use the number). `?` can't be part of a FAT name, so `?file?.tap` finds `{file}.tap` without colliding with `(file).tap`. Substituting `( )` instead would suggest names that give F. `LOAD "tpi:nnn"` (by index) already avoids typing.
  - **Text the 2068 produced** (TAP header names in `tpi:tapdir`, files it saved): send the raw bytes, so names look as the 2068 shows them elsewhere. This is what SEND_MSG2's `expandKeywords` counting is for.
  - **OPEN # channel data:** byte-for-byte, always. `channels.TextIn` currently drops `7Bh`–`7Fh` (§2 #20), so a file the 2068 wrote with `PRINT #4;"a|b"` doesn't round-trip.
  - **`©` in `tpi:info`** (sent as `\*` → `7Fh`) prints as RESET whenever bit 4 is clear. Send `(C)`, or fix it in the ROM by having the 0x86 handler set FLAGS bit 4 before printing (a ROM 2.x change).
  - Worth confirming on hardware first: `PRINT CHR$ 123;CHR$ 125;CHR$ 127` straight after power-on, then again after a `LIST`.
