        INTRODUCTION

        This document details the communication protocol specifications between 
        the operating system of the TS-2068 computer implemented at the release
	1.5 of the TS-PICO ROM OS and the peripherals that support functionalities
	of storage and communication.

        The new basic commands added to the traditional ones use the protocol
        TPI ("Timex Protocol Interface"). In this document you will find examples 
        of these extended commands in Basic (called TPI commands from now on) and
        the detail of the low-level protocol data exchange for each one of them.

        The first part of this document, corresponds to the TPI storage commands
        such as (SAVE, LOAD, VERIFY, MERGE), and to the TPI printer commands 
        (COPY, LPRINT, etc).

        In this document you will also find the communication messages used to 
        load and save the entire memory of the TS2068 to a "SNAPSHOT" file in
        .TMS format called "Timex Memory Snapshot".

        The document also includes the messages used to be able to run other
        operating systems written for this hardware platform. As an example, we 
        can mention CP/M in its 2.2 or 3.0 versions.

        The latest available version of this TPI command extension for the TS-2068,
        is included in the original TS-PICO interface launched this year for the
        40th Anniversary of the TS-2068.

        For more details on the use of the commands and functionalities, please 
        consult the TS-PICO user manual which explains with examples, the 
        implementation of this protocol in the distribution version.

INTRODUCTION:
-------------

THE COMMUNICATIONS PROTOCOL BETWEEN TS-2068 AND TS-PICO,
USES 2 Z80 I/O COMMUNICATION PORTS:

The information exchange is of the MASTER/SLAVE type. 
Communication always originates from the Z80 (MASTER) side via a 
defined PREHEADER, and the response is received from the TS-PICO side. 

An initial request from the SLAVE side cannot be initiated in this release.
This mode is only supported in the hardware that controls the Z80's NMI, 
requesting the transmission of the message to the TS2068 at any time 
(ASYNCHRONOUSLY).

=============================
HARDWARE COMUNICATION LAYER
=============================

(Z80 I/O ADDRESS 14) DATA PORT (R/W)  (D0 - D7 8 BITS DATA)
(Z80 I/O ADDRESS 15) CONTROL PORT (R) (D6 = CONTINUE FLAG) 
                     (In this version, only the read address 
		      of the status port (Input 15) is used.)

In the current version of the communication protocol, 
for each read or write exchanged with the TS-PICO, 
a check of the communication queue status was added 
using bits 4 and 5 of the status register (I/O PORT 15). 

The Z80 will attempt to process the data up to 256 times 
before aborting the operation with a BASIC error. 

This behavior prevents the Z80 from executing an infinite 
loop waiting for communication ready with the TS-PICO.

====================================================================
             STATUS PORT READ I/O PORT 15
====================================================================
D7 = **RESERVED** NOT USED IN THE CURRENT VERSION OF TS-PICO
--------------------------------------------------------------------------
D6=0 Means that ts-pico is busy (processing a message)
D6=1 Means that ts-pico is ready to continue with the 
     interpreter basic program or function in rom.
--------------------------------------------------------------------------
D5=0 Means that the TS-PICO receive queue is full or not ready 
     to receive data. (Z80 Write op is not permitted).

D5=1 Means that the TS-PICO receive queue is ready and 
     accepting new values ??(Z80 Write op is permitted).
--------------------------------------------------------------------------
D4=0 Means that TS-PICO has no data to transmit (empty queue) 
     or the queue is not ready. (Z80 Read op is not permitted).

D4=1 Means that TS-PICO has data to transmit in the queue. 
     (Z80 Read is permitted).
--------------------------------------------------------------------------
D3 -> D0 ** Reserved ** Not used in the current version of TS-PICO **
--------------------------------------------------------------------------

====================================================================

Al the read/write operations wait for the data and if busy, try 256 times
before trigger an automatic error message to avoid that an infinite loop
hangs the computer in case that the ts-pico is not ready.

When the system boots up, all the communication ports are initialized to the
value of 00h in all the bits. The TS-PICO must also correctly initialize the 
data flow control bit values ??on I/O STATUS PORT 15.

=============================
SOFTWARE COMUNICATION LAYER
=============================

THE SYSTEM COMMUNICATES THROUGH A DATA BLOCK WITH MESSAGES PREDEFINED AND
CONTROLLES THEIR INTEGRITY BY A CRC VALUE SENT AS LAST BYTE. (SEE MESSAGES 
DESCRIPTION CHAPTER)

ONCE THE CRC IS SENT, IT MUST BE COMPARED WITH THE LOCAL VALUE CALCULATED 
FROM THE BEGINNING OF THE MESSAGE AND IF THEY MATCH, THE MESSAGE IS VALID,
AND THE RESPONSE SHOULD BE 01 (WHICH MEANS OK). OTHERWISE, YOU SHOULD 
RESPOND WITH THE CORRESPONDING ERROR CODE (SEE TABLE OF ERRORS). 

AS A GENERAL RULE, THE VALUE OF THE ERROR CODE CAN BE CALCULATED AS THE CRC
OF ALL BYTES RECEIVED +01

IF THE RESULTING FINAL VALUE IS 0x01, NO INFORMATION TRANSMISSION ERROR HAS
OCCURRED AND YOU SHOULD PROCEED WITH THE EXECUTION OF THE COMMAND NORMALLY.

IF THE VALUE IS DIFFERENT, THE VALUE RETURNED SHOULD BE A VALID ERROR CODE 
ACCORDING TO THE ERROR TABLE OPTIONS.

IT IS IMPORTANT TO CARRY OUT THE CRC CONTROL TO BE ABLE TO DETECT INCOMPLETE
MESSAGES, WRONG MESSAGES, NOT SUPPORTED MESSAGES, MESSAGES WITH TRANSMISSION 
FAILURES, OVERRUN ERRORS OR LACK OF SYNCHRONISM. IN ALL THESE CASES, THE 
RECEIVER BUFFER MUST BE DISCARDED. THE TS-PICO VERSION DOES NOT SUPPORT 
MESSAGE RETRANSMISSION, THEREFORE IT IS NOT RECOMMENDED TO RESPOND WITH A 
STATIC VALUE (Status Code 0x01 = OK) YOU SHOULD ALWAYS RESPOND WITH THE
CORRECT CODE ACCORDING TO THE CASE, TO AVOID LOSS OF INFORMATION OR
MALFORMED FILES.

FOR THE SLVM COMMANDS 2 BYTES WITH THE SESSION ID ARE SENT. THIS SESSION ID
SHOULD BE THE SAME IN THE HEADER BLOCK AND THE DATA BLOCK. IF THE INFORMATION 
OF SESSION CONTAINS VALUE 0000, THE MESSAGE BLOCK MEANS THAT IT WAS NOT GENERATED
FROM A BASIC COMMAND.

**NOT ALL DOCUMENTED FUNCTIONS OR PROTOCOL DEFINITIONS ARE AVAILABLE IN THIS ROM VERSION**

BELOW IS AN EXAMPLE OF THE TYPICAL BASIC SLVM GROUP (SAVE).
THE COMPLETE COMMAND INCLUDES THE FOLLOWING PHASES:
1) PRE-HEADER MESSAGE
2) RETURN ERROR CODE
3) WAIT FOR EXECUTION
4) HEADER BLOCK
5) WAIT FOR EXECUTION
6) RETURN ERROR CODE
7) DATA BLOCK
8) WAIT FOR EXECUTION
9) RETURN ERROR CODE

IN THE PHASE OF WAIT FOR EXECUTION A 2.8ms TIMER IS ACTIVATED. WHILE THE 
TS-2068 IS WAITING THE CONTINUE SIGNAL, READING THE BIT 6 AT PORT 0x0F, 
THE TS-PICO SHOULD EXECUTE  THE COMMAND AND RESPOND DURING THAT PERIOD OF TIME.
IN CASE THE TIMER EXPIRES WAITING FOR THE CONTINUE SIGNAL, AN ERROR 
J - INVALID I/O DEVICE (TIMEOUT CONDITION) IS RETURNED AUTOMATICALLY.

For debugging and documenting the protocol, the TPI tracing module can be used 
(enabled only in the debug version of the ROM). This protocol uses secondary
communication ports 30 and 31 of the Z80 to send the values ??exchanged in the 
low-level TPI communication messages between the TS-PICO and the Z80. 
It is recommended to use at least a 16-bit counter on the receiving side of 
these debug writes to use the counter's value as a relative time unit between 
the message bytes. 
Send at least three binary values ??to the data logger: 

1 = TIMESTAMP (BYTE NUMBER), 2 = OPERATION TYPE (RD/WR), 3 = VALUE.

The presentation software can format it in the tracing format used in this document.

USING STATUS CODE > 080H
-------------------------

AT THE LAST PHASE OF THE COMMAND, IF THE STATUS CODE RECEIVED IS GREATER 
THAN 080H, IT MEANS THAT ADDITIONAL INFORMATION IS REQUIRED BY THE SPECIAL 
FUNCTION INVOKED AND SHOULD BE ADDED EXTRA DATA TO THE COMMUNICATION PROTOCOL.
